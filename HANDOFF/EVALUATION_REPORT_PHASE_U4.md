## 1. エグゼクティブサマリー

申込導線・保護者向け体験は単一校舎・245名規模の Pure Play としては**完成度が高い**水準にある。Phase U-3-A の本番ハードニング（二重申込・クォータ・LockService・レート制限）と Phase U-3-B のマイページ実装で、当初の MVP は明確に超えた。一方で、**運用の見える化（BI）・テスト自動化・マルチテナント化**が空白で、ここを埋めない限り「動くシステム」から「経営ダッシュボード付きの SaaS 候補」には届かない。Phase U-4 のモジュール化（Code.gs 2043 行 → 16 ファイル / index.html 4144 行 → 47 行 + 30 パーシャル）は保守性を**劇的に**改善し、次フェーズに進む土台として合格。

総合 **★4.1 / 5.0**。claude.ai 評価（★4.2）とほぼ一致するが、技術基盤を半段下げ、デザインを半段下げる（後述）。

## 2. カテゴリ別評価

### 2.1 申込フロー UX — ★4.7 / 5.0

**良い**:
- ?page=mypage 別画面分離で初回申込フローに不要素が混入しない
- 連打防止・入金前領収書非発行・残席ぼかし表示など、**現場の実際の事故シナリオに対する手当て**が入っている
- 申込番号 SS-XXXXXX をメールに表示 → マイページ動線が自然

**イマイチ**:
- 申込番号列の取り扱いが `getRange(newRow, appNumCol)` の position 依存で、列順を変えるだけで割れる（`04_enrollment.gs`）。ヘッダ名で引く `getColIndex()` 系ヘルパに揃えるべき
- 旧申込（申込番号列ができる前のレコード）がマイページからアクセスできない → エラーメッセージ案内のみ。245 名規模なら手動で埋められるが、今期中に一度バックフィルするべき

claude.ai は ★5.0 だが、上記の technical debt が残るため減点。

### 2.2 保護者向け機能の網羅性 — ★4.5 / 5.0

**良い**:
- 申込内容 / 入金状況 / ウェイティング / 変更希望、と保護者の「知りたい・直したい」を 5 ブロックで網羅
- 領収書再送が `is_paid` のみ → 会計原則を UI で守っている
- 変更希望は自動キャンセルせず学校宛メール → 業務責任の所在が崩れない

**イマイチ**:
- 「キャンセル待ちが何番目か」の表示（Block 3）の更新タイミングが申込時点スナップショットのままだと、保護者の問い合わせが減らない。ロード時再計算が必要なら `15_mypage.gs` 側で対応するべき
- 受講科目の追加申込（増コマ）導線がない。これが要件外なら問題ないが、5月24日の1次締切後 → 6月8日開講までの間に「やっぱり追加」が来るのは経験則として確実

### 2.3 学校側の運用機能 — ★3.5 / 5.0

**良い**:
- outputRoster / outputSummary / outputTimetable の 3 レポートは 245 名規模の単一校舎運用としては最低限を満たす
- マイページの変更希望が学校宛メールに集約 → 業務フロー側のオーバーヘッド少

**イマイチ（ここが本システム最大の弱点）**:
- **BI ダッシュボード（売上推移・稼働率・申込推移の可視化）が未実装**。これは claude.ai 指摘の通りで、本評価でも同意見
- エラー監視が `console.error` のみで外部アラート（Slack / メール）連携なし → 障害発生に気付くのが事務局の問い合わせ起点になる
- 締切前後の申込スパイクに対する**稼働率モニタ**がない。245 名想定でも、5/24 直前の 24h で 60〜80 名集中が経験的に起きる。ここで Gmail クォータ（1日 100 通）に当たると即事故

claude.ai ★4.0 → 本評価 ★3.5。BI 不在の運用負荷を重く見ている。

### 2.4 技術基盤・スケーラビリティ・保守性 — ★3.5 / 5.0

**良い**:
- Code.gs 2043 行 → 16 ファイル（00_constants 〜 15_mypage、平均 ~150 行）の分割は健全。責務境界が読みやすい
- index.html 4144 行 → 47 行のオーケストレータ + 30 パーシャル。CSS / partial / page / js / mp_ の prefix 規約も意図が読める
- LockService・rate limit・duplicate detection・safeSendEmail のハードニング系がすべて入っている
- `getSchoolConfig()` でシートから校舎設定を読む下地はある

**イマイチ**:
- **自動テストがゼロ**。Apps Script の制約はあるが、純関数レイヤ（`01_utils.gs` の `_rateLimitOk` / 申込番号採番 / 重複検知）だけでも `clasp` + Jest 系のスモークテストは可能。今後の改修で必ず効く
- マルチテナント化は「下地はある」止まり。SCHOOL_EMAIL / SCHOOL_NAME 等のハードコード除去・テナント ID による Sheet 分離・PropertiesService の名前空間分離が未着手
- PropertiesService にレート制限カウンタを置いているが、**TTL 自動失効ではない手動管理**。長期運用でゴミが溜まる
- `15_mypage.gs` の認証で 5 回失敗 → 15 分ロックは適切だが、**ロックキーがメール単位** だと大量の入力試行に弱い（IP も併記したいが Apps Script では取れない / `e.parameter` トークン併用が現実解）

claude.ai ★3.5 と一致。テスト不在を最大の減点要因とする。

### 2.5 デザイン・ブランディング — ★3.5 / 5.0

**良い**:
- mp_styles.html で保護者マイページの CSS が独立。本体ページに影響しない
- 駿台ミシガン国際学院のブランドトーンに合わせやすい構造

**イマイチ**:
- 本体 index.html 側のスタイル統一性は読める範囲では平均的。意匠面で「駿台ミシガン国際学院ならでは」の表現は弱い
- スマホビュー最適化の検証エビデンスが本評価範囲では確認できなかった（保護者の 7 割以上はスマホからの申込と推定）

claude.ai ★4.0 → 本評価 ★3.5。意匠の独自性が薄い点で減点。

### 2.6 法務・コンプライアンス — 対象外（閉じたコミュニティ前提）

駿台ミシガン国際学院の在校生・関係者を対象とした閉じた申込で、不特定多数向け SaaS ではない。特定商取引法表示・個人情報保護方針の表記義務は学校本体側に従属。本システム単体での評価は対象外とする。

ただし SaaS 化する場合は別基準（後述 2.7）。

### 2.7 SaaS 化への布石 — ★3.5 / 5.0

**良い**:
- `getSchoolConfig()` による外部化の素地
- ファイル分割により、テナント固有ロジックを差し替える境界が見える
- 申込番号 prefix（SS-）はテナントごとに変えやすい設計

**イマイチ**:
- ハードコードされた校舎情報が複数ファイルに散在（前任の調査メモより）
- 課金・利用量計測・テナント管理 UI なし
- データ分離（Sheet レベル / Workspace レベル）の方針が未定
- そもそも Apps Script + Sheets バックエンドは**100 校舎規模で破綻**する。SaaS 化を本気で目指すなら Cloud Run + Firestore / Cloud SQL への移植が前提

claude.ai ★4.0 → 本評価 ★3.5。「布石」としては OK だが「レディネス」は低い、と差をつけたい。

## 4. claude.ai 評価との差分分析

### 4.1 一致している点
- 申込導線・保護者機能は高水準
- BI ダッシュボードが空白なのは共通認識
- 技術基盤 ★3.5 で同点 — テスト不在 / マルチテナント未着手の評価軸が一致

### 4.2 本評価のほうが辛い点
- **運用機能（-0.5）**: BI 不在の運用負荷を「将来課題」ではなく「現在進行形のリスク」と見ている。5/24 直前のスパイクで Gmail クォータに当たる事故シナリオが現実的
- **デザイン（-0.5）**: 意匠の独自性・スマホ最適化の検証エビデンスが薄い
- **SaaS 布石（-0.5）**: Apps Script + Sheets で 100 校舎は破綻するという**アーキテクチャ天井**を明示的に減点

### 4.3 本評価のほうが甘い点
- **申込フロー UX（-0.3）** は claude.ai が ★5.0、本評価が ★4.7。技術的負債（列インデックス依存・旧申込問題）を見ているため減点したが、保護者体験そのものは ★5.0 で良い

### 4.4 自己評価バイアスの警戒
Code 側は「自分が実装した部分」をやや甘く採点する傾向がある。今回は意識的に**技術基盤・SaaS 布石は claude.ai と同点 or それ以下**に置いた。逆にデザインとマルチテナントは「Code は実装していない / 検証していない」ので冷静に低めに振った。

## 7. SaaS 化レディネス

**結論: 現時点では SaaS として外販できない**。布石はあるが、以下が満たされるまで「内製ツール」と位置づけるのが妥当。

### 7.1 必須条件（SaaS 外販に向けて）
1. テナント分離（データ・認証・課金）
2. 監視・SLA 体制
3. テスト自動化（最低でも申込・決済・メール送信のクリティカルパス）
4. アーキテクチャ移植（Apps Script + Sheets → Cloud Run + Firestore など）
5. 営業・サポート体制

### 7.2 推奨アクション
- 短期（〜2026年7月、開講後）: 駿台ミシガン国際学院での運用実績を積む。BI・アラート・テストを足す
- 中期（2026年9月〜）: 「同業 1 校で β 導入」を現アーキで試す。20〜50 校舎までは現アーキで戦える可能性が残る
- 長期（2027 年以降）: アーキ刷新の意思決定。ここで Apps Script を捨てる覚悟が要る
